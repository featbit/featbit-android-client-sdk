# FeatBit Android Client SDK Development Plan

Updated: 2026-10-04. Phases 1–6 and Phase 7 tooling are implemented. The 0.1.0 local matrix and hosted consumer CI passed; the maintainer confirmed physical-device and deployed-service validation. Signing, Central publication and fresh-download verification remain pending. See [current evidence and limitations](./docs/verification.md#release-readiness--2026-10-04). The phased scope below records the original implementation plan; Java/Kotlin samples have since been implemented.

The repository contains the Library build, local and online runtime, events, persistence, real Android lifecycle integration, independent AAR consumers and CI configuration. See [verification evidence](./docs/verification.md) for the boundary between implemented behavior, executed checks and remaining acceptance. Samples and remote publication remain separate work.

## 1. Goals and agreed boundaries

- Develop and independently publish the FeatBit Android Client SDK in this repository using Kotlin **1.9.25**.
- Support both Java and Kotlin through the public API. Synchronous in-memory reads are the foundation; asynchronous operations provide Java-friendly callbacks and Kotlin suspend adapters, and change subscriptions provide listeners and Flow adapters.
- Each SDK instance serves one current user context and receives server-evaluated results. It does not implement client-side targeting, segments, or experiment assignment.
- The OpenFeature Provider is a separate product in another repository, planned to use Kotlin **2.2.10**. This project does not depend on OpenFeature, expose its types, or implement the Provider.
- iOS, Kotlin Multiplatform, and Compose-specific bindings are outside the first release of this project.
- The existing customer Android SDK and JS SDK can inform protocol and behavior analysis, but their implementations must not be assumed to conform to the new specification. Check licenses and attribution requirements before reusing third-party code.

## 3. First-release capabilities

The following is the proposed first-release scope. Deferring optional capabilities does not remove mandatory contracts, and deferred capabilities must be explicitly identified in the capability list.

| Capability | First-release scope |
| --- | --- |
| WebSocket synchronization | Required and the default mode; includes application-level heartbeats, recovery, and terminal rejection |
| Foreground HTTP Polling | Included as an explicit mode, sharing the Streaming storage and identity contracts |
| Android lifecycle and network integration | Automatic process/network/Doze integration; internal testable platform boundary, no public manual-visibility hooks |
| Background synchronization | Android background polling is included but disabled by default; explicit enablement remains subject to platform execution opportunities; otherwise synchronization pauses |
| Transition grace period | Defaults to 0; a bounded duration is configurable and affects only flag synchronization |
| Initialization, Identify, Flush, Close | Bounded asynchronous results with explicit errors, timeouts, supersession, and closure outcomes |
| Runtime setOffline / setOnline | Included, with an explicit offline-state query and bounded transition results; managed separately from background suspension, network loss, disableEvents, and permanent closure |
| getConnectionInformation / getVersion | Included; immutable synchronization-state snapshot and actual SDK artifact version, both synchronous local reads without networking or diagnostic telemetry |
| Typed and detailed evaluation, read-all | Required; synchronous in-memory reads returning stable snapshots |
| Detailed evaluation reasons | Included; all detailed APIs always return a FeatBit reason category and retain server explanations when available; no evaluationReasons switch |
| Dedicated integer evaluation | No intVariation / intVariationDetail or other integer-specific APIs in the first release; retain Number and its detailed evaluation without adding an Int flag type |
| Generic variation / variationDetail | Included; convert according to the declared flag type and return a unified immutable value model usable from Java/Kotlin; detailed results include evaluation reasons |
| Change and status subscriptions | Global flag changes, individual flag changes, and readiness/synchronization status; Java listeners return closeable handles, with Kotlin Flow adapters |
| JSON evaluation | Included; raw JSON string access and parsed JSON helpers usable from Java/Kotlin |
| Persistent flag cache | Enabled by default; can be disabled or cleared; five-context LRU per namespace, no byte cap or age expiry |
| Bootstrap | `bootstrap(flags)` supplies immutable all-user defaults; bootstrap first at creation, target-context cache first after Identify; no public scope type or context-bound variant |
| Event collection and in-memory queue | Required, bounded capacity, deduplication per flush group; periodic flush defaults to 30 seconds |
| Additional JSON data for Track | Not provided in the first release; Track retains an event name and optional numeric value (default 1.0), with no additional JSON payload parameter |
| disableEvents | Included, default false; true disables evaluation and Track event collection and delivery while flag synchronization, evaluation, and subscriptions continue |
| SDK diagnostic telemetry and opt-out | No diagnostic uploads, sampling interval, or dedicated diagnosticOptOut switch in the first release; retain safe local logs, failure states, and loss counters |
| Private attribute filtering for analytics | SDK-side filtering included, disabled by default; supports named custom attributes and all custom attributes; server changes may follow and are not a prerequisite |
| Event flush on background transition | Included as a configurable capability with a bounded budget; freeze the default switch and budget in Phase 1 |
| Persistent event queue | Deferred; document possible event loss on process termination in the first release |
| Automatic anonymous key | Included with explicit enablement; random application-scoped identifier with persistence, reuse, and reset; explicit user keys take precedence |
| Automatic device/application attributes | Included but disabled by default; sample the fixed field schema at creation and Identify when enabled |
| Automatic Streaming → Polling fallback | Included, configurable and disabled by default; when enabled, sustained temporary foreground Streaming failures trigger Polling, covering both initial connection failures and interruptions after connection |
| Automatic recovery to Streaming | Included together with automatic fallback; bounded probes after cooldown take over only after successful synchronization; explicit Polling never probes Streaming |
| Multiprocess/cross-application sharing | Unsupported; multiple instances within one process must isolate data and events |
| Unified multi-environment management | No named-environment manager or cross-environment bulk operations in the first release; applications may manage separate clients with independent configuration, Identify, online state, Flush, and Close, preserving environment data/cache/event isolation |
| Custom data source/synchronizer | Included; public Java/Kotlin-friendly factory, data source lifecycle, and controlled update sink replace the built-in synchronization path |
| Public TestData utility | Included; ready-to-use local test data source and flag construction/update tools for Java/Kotlin, enabling evaluation and subscription tests without a server |
| Custom persistent store | No public replacement entry point in the first release; retain internal test substitution and existing cache configuration/clear operations |
| Custom platform | No public replacement of the entire platform in the first release; retain internal test substitution and explicit host lifecycle hooks |
| Custom EventProcessor | No public event processor replacement entry point in the first release; retain an internal substitution boundary for tests; the built-in processor manages events under the agreed configuration and contracts |
| Custom request headers | Included for built-in synchronization and event requests, protecting SDK authentication and protocol-required headers |
| Wrapper metadata | No dedicated wrapper library name/version configuration or automatic reporting in the first release; SDK identification and existing application attributes remain available |
| Hooks / Plugins | No public evaluation/Identify operation hooks or general plugin system in the first release; agreed change subscriptions, custom data sources, and host lifecycle hooks remain available |

## 5. Project structure and internal architecture

Use one Android Library publishing module and minimal independent Java/Kotlin consumer test projects. Samples/demo Apps were deferred from the original core implementation; Java/Kotlin samples are now available under `samples/` and do not replace independent consumer acceptance. Consumer projects are test fixtures for public API compilation, actual AAR consumption and R8, not demonstration products. The first release publishes one core AAR. Java/Kotlin adapters share state and business logic rather than maintaining two implementations.

Divide internal responsibilities as follows; each area need not be a separate Gradle module:

1. Public API: configuration, users, evaluation results, status, asynchronous results, subscriptions, and closure.
2. State coordination: current context, generation, synchronization permissions, lifecycle, offline, and terminal states.
3. Result store: immutable memory snapshots, batch commits, cursors, bootstrap, and cache provenance.
4. Synchronization transport: WebSocket, Polling, tokens, heartbeats, requests, and recovery scheduling.
5. Persistence: asynchronous reads, atomic replacement, ordered writes, invalidation, retention, and clearing.
6. Event processing: capture at call time, collection eligibility, flush groups, batches, retries, and waiters. Keep an internal substitution boundary for deterministic tests; do not publish an EventProcessor interface, factory, or injection configuration in the first release. The built-in event pipeline continues to support disableEvents, capacity, flush interval, private attribute filtering, and request headers; these do not constitute processor replacement.
7. Android integration: process visibility, network state, main-thread notifications, and resource release.
8. Diagnostics: application-controlled logs, safe-field filtering, rate limiting repeated errors, failure states, and loss counters; all subsystems share this boundary.

Use serialized coordination or equivalent atomic control for state changes. Synchronous evaluation reads immutable memory snapshots without blocking on disk or networking. Network callbacks, timers, and cache jobs validate their generation before committing. Do not invoke application code while holding state locks.

Use the configuration builder method `bootstrap(flags)` in Java and Kotlin. Supplying immutable initial values declares that they are application defaults for every user, including Identify and anonymous transitions. Do not expose an ApplicationDefaults type or context-bound variant/scope selector; personalized bootstrap results are outside this option's contract. At initial client creation, configured bootstrap, including an explicitly empty set, still takes precedence over cache and requests cursor zero. After every accepted identity transition, prefer the target environment/full-context cache and its paired cursor; a valid empty cache is also a hit, and missing keys are not filled from bootstrap. Only a cache miss/unavailability (including disabled caching, corruption or read failure) selects configured bootstrap with cursor zero, otherwise an empty local view. While the asynchronous target-cache decision is pending, reads return caller fallback and never the previous user's values; network synchronization need not wait. Revalidate both cache hits and miss-triggered bootstrap publication against the existing load/generation/epoch rules: remote commits, another Identify, clear or Close fence obsolete outcomes. No remote omission later reactivates bootstrap after cache was selected. Preserve existing Identify session isolation and completion behavior, local origin, no bootstrap evaluation analytics and no remote readiness from local data. Verify Java/Kotlin builder usage, immutable inputs, generation-local shadow rules, valid-empty versus absent cache/bootstrap and cache/network races. The method name is settled; validate concrete flag/collection types and binary signatures in Phase 1.

Close must start bounded cleanup regardless of ordinary operation-result capacity or blocked application callbacks. Repeated calls reuse the operation/deadline and immutable final result. Preallocating a dedicated close result/initial completion lease is an implementation option, not a frozen requirement. Additional completion registrations may be bounded and rejected independently, without rejecting cleanup or making its final result inaccessible. Verify cleanup and result settlement under saturated ordinary completion capacity and a blocked UI dispatcher.

Agreed Identify isolation: replace the synchronization session on every accepted Identify instead of sending a new context on the existing WebSocket. The following WebSocket steps apply when Streaming is the effective mode. Explicit, fallback, or temporary background Polling replaces its polling session instead; Identify must not recreate a WebSocket in those modes. A generation is a client-local context-switch identifier, not a user attribute, server flag timestamp, or protocol field. The server need not echo it.

- Validate and capture the new user first; invalid Identify leaves the current session unchanged. Accepting a valid Identify atomically advances the generation, switches local context, invalidates the old synchronization session, and settles the old Identify waiter as superseded.
- Close the old WebSocket. When execution is permitted, create a new WebSocket and bind the connection and callbacks to the generation and session identifier captured at creation. Offline, background suspension, unavailable networking, or terminal synchronization only permit a new logical context, not bypassing network restrictions.
- Messages, errors, close callbacks, reconnect timers, and responses already being processed from the old connection cannot update the new context, settle new waiters, change new session state, or initiate recovery. Validate authority at receipt and final commit; do not assign the current generation to a message only when it arrives.
- Reconnection within the same context also replaces the connection session identifier, invalidating callbacks from the replaced connection. Context generation and connection session identifier jointly determine commit authority.
- Polling requests and asynchronous cache work also capture their context generation when started. Cancellation releases resources; commit-authority checks ensure correctness. Do not assume cancellation prevents later callbacks.
- Apply these rules to attribute changes with the same key and to A→B→A transitions. New sessions use only data and cursors matching the complete new context; otherwise request a full snapshot. The first release accepts connection setup overhead on Identify to avoid depending on request-correlation fields absent from the protocol.

Provide internal substitution boundaries for clocks, scheduling, networking, storage, and lifecycle to support deterministic tests. Duration budgets use elapsed time including device sleep; protocol timestamps use wall-clock time; cursors come only from remote flag timestamps. Cancelling a caller's wait must not cancel ongoing SDK recovery.

### Anonymous identity, automatic attributes, and background polling

- Generate an anonymous key only when anonymous mode is explicitly enabled and no key is provided. An explicitly supplied invalid key remains an error and is not silently replaced. With this capability disabled, the application must supply a valid user. Use a random application-scoped identifier, not hardware or advertising identifiers. Establish valid identity before memory evaluation, cache lookup, networking, or event capture; disk reads must not block the main thread.
- Provide explicit operations to return to anonymous identity and reset the anonymous key, reusing bounded Identify results and generation isolation. Login uses an explicit user without automatically linking or merging anonymous and signed-in events. Returning to anonymous reuses the saved key by default; reset generates a new key. Old cache data cannot become data for the new identity during reset; accepted events retain their original identity. Reset does not erase all historical cache or previously sent data.
- Use one public identity outcome (success, failure, superseded, closed or timeout) under the common Identify conventions; keep persistence stage, repository revision and adoption authority internal or in safe diagnostics. Persist before adopting a new reset key; successful adoption alone does not establish remote readiness. Timeout/supersession/Close or caller-wait cancellation cannot promise rollback of an already admitted shared write. Test late persistence without stale adoption or a second result, and subsequent anonymous operations reading the actual persisted key.
- Anonymous identifier storage is independent of flag-cache enablement/clearing and Close. Coordinate initial generation across instances in the same process to avoid competing identifiers. Phase 1 fixes scope, asynchronous read/write failure results, reset persistence ordering, adoption by other active instances, and uninstall/reinstall, backup/restore, and explicit clearing policies. Do not claim restart stability after failed persistence. Other instances must adopt the new identity through the specified creation/anonymous transition operations, not silently switch identity during evaluation.
- Anonymous preparation reservations supersede older pending preparations only, leaving current committed-context initialization/Identify waits active. Only acceptance of a fully prepared replacement context supersedes those waits. Preparation failure preserves the current context and its pending waits; already settled outcomes remain unchanged. Keep preparation-operation authority distinct from committed-context generation authority.
- When automatic attributes are enabled, collect only published fields under the reserved `featbit.sdk.` prefix. Define each field's wire name, meaning, Android source, string representation, and availability. Freeze the first-release field set in Phase 1, individually confirming application identity/version, OS version, device information, and other candidates. Do not collect hardware/advertising identifiers. Omit unavailable fields rather than inventing empty values. Conflicting caller attributes reject creation/Identify and preserve the old context. When disabled, do not collect these fields or reserve the prefix.
- Sample automatic attributes at creation and every valid Identify, including anonymous transitions, before cache lookup, producing an immutable effective context. Resample even for the same user key; attribute changes use a new generation and matching-cache rules. Foreground resumption, evaluation, and event sending alone do not resample. Old events retain their snapshot. disableEvents does not remove automatic attributes needed for synchronization. A new instance with collection disabled cannot reuse cache for a different attribute context.
- Background polling is independent of automatic fallback and disabled by default. Enabling it online requires validation of the Polling endpoint, background interval, and request/retry limits even when foreground mode is Streaming with fallback disabled. Foreground and background intervals are separate; Phase 1 fixes defaults, minimums, and scheduling. Offline retains endpoint exemptions. Custom conflicts with built-in background polling configuration and retains the background-pause contract in the first release.
- With background polling enabled, creation/Identify in the background may start permitted Polling for the latest context; a valid remote commit may complete initialization/Identify without a foreground transition. Defer work when execution opportunities or networking are unavailable; caller waits remain bounded. Entering the background invalidates the foreground source and recovery candidate first. When background polling is enabled, do not retain a foreground Streaming grace connection; hand over directly to background Polling. The default pause path still follows the configured grace period. All transitions retain complete context, matching snapshots, and cursors.
- Background Polling is a temporary lifecycle transport, not Streaming failure fallback. Foreground resumption stops the background source and rejects late callbacks: non-fallback Streaming resumes Streaming; a fallback instance resumes foreground Polling and probes under cooldown policy; explicit Polling resumes its foreground interval. Status distinguishes temporary background mode from failure fallback. Do not run automatic recovery candidates in the background.
- Background polling does not start ordinary analytics delivery. Event grouping and bounded transition flush retain their contracts. Respect Doze, App Standby, suspension, and process death. Do not promise exact intervals or continuous execution, catch up missed polls, or require a foreground service, wake lock, or battery exemption.

### Custom request header contract

- Provide Java/Kotlin configuration for custom request headers, defaulting to empty collections copied and frozen at creation. Support separate synchronization endpoint headers (WebSocket handshake, foreground/background Polling, and recovery candidate handshake) and event endpoint headers. Do not implicitly send synchronization gateway credentials to a separate event endpoint; callers must explicitly configure both groups to share headers. The first release uses static configuration without dynamic credential-refresh callbacks; changing header values requires a new instance.
- Add extension headers without overriding SDK authentication, SDK identification, or protocol-required headers. Check duplicates and conflicts case-insensitively. Protect Authorization, Host, Content-Length, Content-Type, Connection, Upgrade, Sec-WebSocket-*, and other SDK/transport-managed headers; freeze the complete list in Phase 1. Invalid names, CR/LF, duplicates, and protected names produce configuration errors rather than silent overwrites. Headers are not user attributes and do not affect context hashing, flag-cache matching, or event deduplication.
- Built-in retries, reconnections, background transitions, and fallback/recovery use the same immutable configuration. Disable automatic redirects for built-in synchronization and event requests, both same-origin and cross-origin. Do not follow Location or forward extension headers to another destination; require the final endpoint directly. Specify bounded error/recovery handling for 3xx, never treating it as valid synchronization or delivery. Event delivery remains subject to finite budgets.
- Treat all header values as potentially sensitive; exclude them from logs, exception messages, and diagnostics. When needed, log only filtered header names. Custom headers do not change offline, disableEvents, or TestData network gates; TestData makes no network requests.
- Custom sources own their networking; the SDK does not promise synchronization header injection for them. Custom plus built-in synchronization header configuration is a transport-specific conflict validated before creation. Their independent event path may still use SDK event headers. Extension headers support gateway authentication/routing and similar needs; they do not replace the FeatBit client key or introduce wrapper-specific metadata.

### Public data source extension contract

The extension scope aligns with LaunchDarkly Android's traditional public data source capability: a public factory and lifecycle, without replacing the persistent store or entire platform. It does not promise to reproduce all LaunchDarkly components or custom FDv2 pipelines. The reference baseline is source commit `0f40e44b989d46e7d4a8c0c0475029c85c5bbe08`: [LDConfig](https://github.com/launchdarkly/android-client-sdk/blob/0f40e44b989d46e7d4a8c0c0475029c85c5bbe08/launchdarkly-android-client-sdk/src/main/java/com/launchdarkly/sdk/android/LDConfig.java) and [DataSource](https://github.com/launchdarkly/android-client-sdk/blob/0f40e44b989d46e7d4a8c0c0475029c85c5bbe08/launchdarkly-android-client-sdk/src/main/java/com/launchdarkly/sdk/android/subsystems/DataSource.java).

- Provide a public factory through which the SDK creates a separate data source for the current context and synchronization session, with start, asynchronous stop, and status/error reporting contracts. The SDK manages replacement and deactivation during Identify, pause/resume, offline, terminal failure, and closure, without application access to the internal coordinator. Factories receive immutable context and required configuration, not a mutable internal store, control over generation, or platform implementation.
- Sources submit full snapshots, patches, and status through a write-only update sink. Use explicit immutable FeatBit types such as FlagRecord, FullUpdate and PatchUpdate with `key`, `variation`, `variationType`, `timestamp`, archival state, reasons, and top-level `variationOptions`. The retiring `sendToExperiment` field is excluded from the Android model. In-process submissions have no schemaVersion field, runtime schema negotiation or V1 type suffix; manage evolution through the SDK's source/binary API compatibility policy. Record timestamps, remote cursors and persistent cache format versions remain necessary and distinct. The SDK handles validation, atomic commits, cursor rules, persistence, notifications, and event eligibility. Missing, invalid or ambiguous selected-variation metadata suppresses evaluation events; the SDK never invents variation IDs or performs experiment sampling locally. Initialization requires valid data committed for the current session, not merely factory creation or connection success.
- Custom sources are trusted extension code selected by the application and responsible for truthful provenance, service results and analytics metadata. The SDK checks structure, session/context authority, timestamps and variation mapping, but cannot authenticate the server origin of structurally valid extension-supplied data. LOCAL sources cannot obtain remote confirmation or evaluation-event eligibility by attaching analytics metadata. Conforming REMOTE sources may supply metadata for eligible events under the normal SDK gates; this does not guarantee detection of fabricated data from a misbehaving REMOTE source.
- Bind each sink to its creation-time context generation and session identifier. Replacement, suspension, or closure invalidates it; later update/success/error callbacks cannot commit, settle new waiters, or trigger recovery. Stop requests are bounded; late-callback isolation does not depend on timely third-party cancellation. Start each instance once and never reuse it for a new user.
- Custom submissions prepare and commit synchronously on the caller's thread, returning one already-settled standard operation handle with the final result. Inspect SourceUpdateResult.code for commitment or rejection, including explicit validation reasons without advancing its baseline. The current sink emits COMMITTED, INVALID, INACTIVE or CLOSED; the public BACKPRESSURED and SUPERSEDED values are not currently emitted. Reuse common asynchronous callback delivery and its registration capacity limits, without a submission queue, admission sequence or update-specific timeout timer. Caller wait timeouts cannot preempt synchronous submission; callback detachment does not undo a commit, and the result remains queryable. Sources own ordered correction/resubmission and must not treat rejected work as committed. Validate this contract through Java/Kotlin consumers and TestData.
- Custom replaces the entire built-in Streaming/Polling synchronization path and does not automatically participate in built-in fallback or candidate recovery. A custom factory conflicts with explicitly selected built-in transport modes, transport-specific settings, or enabled fallback/recovery; reject before creation. Implicit built-in defaults are not conflicts. Custom may manage its own transport but must obey SDK synchronization permissions and stop contracts. The SDK starts no concurrent built-in connection. Status identifies Custom and retains readiness, interruption, and terminal states.
- Validate only enabled paths. Missing unused built-in Streaming/Polling endpoints do not invalidate Custom; the factory contract validates its own options. Validate event delivery independently against FeatBit event configuration. Offline must not start Custom, and recreating an extension instance cannot bypass terminal synchronization failure.
- Define threading, error results, and resource ownership for factory creation, start, stop, and update submission. Application implementations must not block the coordinator or UI thread; submit large snapshots off the UI thread. Isolate recoverable exceptions and invoke no extension code under state locks. Non-overlapping submissions retain call order; overlapping submissions are ordered by actual commit under the state gate, with preparation retried if the captured view changed. Keep lifecycle executor and callback registration capacity limits separate from synchronous submission processing. The SDK stops sources it creates; release shared caller resources only after explicit ownership transfer. Document that uncooperative third-party threads cannot be forcibly terminated.
- Use a fixed extension executor with a bounded scheduling queue; require factory/start to return promptly and stop to report asynchronous completion. Keep exception isolation, stop deadlines, session invalidation and Close independence. Scheduling overload reports ordinary source failure; blocked stop reports incomplete cleanup. A timed-out invocation occupies its slot until exit; do not create compensating threads. No global source-lifecycle lease registry or reserved cleanup-capacity/recovery subsystem is required. Test blocked/throwing calls, queue rejection and late callbacks; document extension responsibility for cooperative resource cleanup.
- Freeze minimal public extension types and compatibility policy in Phase 1. Internal fake clocks, stores, and platform substitution remain internal. Java and Kotlin consumers must be able to implement sources in independent projects without internal-package access or SDK test-source dependencies.

### Public TestData contract

- Ship a public utility in the core AAR, in a separate namespace named in Phase 1, built on the public factory and controlled update sink. Consumers need no SDK test sources or internal packages. It supports App unit/UI tests and local demos, not server targeting, segment, or experiment-assignment simulation, and does not replace real protocol integration tests.
- Support initial flag collections, Boolean/Number/String/JSON values by key, updates, deletion, and re-addition. Bounded completion results indicate commitment to the bound client's current valid session, with normal subscription notifications. Inputs/results are immutable; invalid updates preserve existing state. Generate flag-change timestamps in Unix milliseconds internally using a controllable wall clock, without caller-managed timestamps. Keep submission ordering separate from time; cover same-millisecond changes and clock rollback when implementing TestData. Batch updates, if offered, commit atomically; freeze APIs in Phase 1.
- All users share the same explicitly configured values; no per-user targeting rules in the first release. Identify resubmits the current test snapshot for the new context, while old sessions cannot commit. An initial valid snapshot, including an empty collection, may complete initialization. Report Custom/TestData local readiness without claiming a real service connection.
- TestData makes no real network requests. Its configuration entry point fixes analytics to disabled, requires no client key or remote endpoints, and starts no Streaming, Polling, background polling, or recovery probes. Explicit event enablement or built-in transport options cause configuration conflicts rather than silent ignoring. Test snapshots remain in memory without production flag-cache reads/writes or fabricated remote provenance/evaluation-event eligibility. Freeze composition with immutable options in Phase 1.
- Network-free testing does not mean offline=true: TestData starts and submits under the Custom lifecycle. Explicit setOffline, default background suspension, and Close still stop its session. While inactive, callers may modify the saved test collection but cannot commit to the inactive client or settle synchronization waiters. Results distinguish saved-only from applied. Resumption submits the latest full snapshot, without replaying all intermediate changes.
- One TestData instance binds to one active client in the first release; duplicate binding returns a clear error. Use independent utilities and clients per test, not static shared data. Close releases binding/subscriptions without destroying the caller-owned configuration object; later binding to a new client is allowed, with old callbacks still invalid. Phase 1 fixes concurrent update/Identify/stop ordering, results, capacity, and ownership.

### Connection information and SDK version query contract

- Expose `getConnectionInformation()` and `getVersion()` to Java/Kotlin. The former returns an atomically read immutable status snapshot; the latter returns the actual build-time SDK artifact version matching publication, not the host App, server, or Kotlin version. Both synchronously read memory/build constants without disk/network I/O. Final status and version remain queryable after Close.
- Include configured mode (Streaming/Polling/Custom), effective mode, synchronization state (initial wait, healthy, retrying after failure, paused, terminal, closed), pause reasons (explicit offline, background policy, unavailable networking, etc.), current-context local data availability, and remote synchronization confirmation. Multiple pause reasons may coexist; network loss cannot overwrite offline intent. Valid empty snapshots can be ready; flag count is not a readiness test. Explicitly indicate no active transport when paused/closed, rather than presenting a retained resumption target as connecting.
- Distinguish failure-fallback Polling from temporary background Polling and expose recovery state (not recovered, cooling down, probing). Effective mode stays Polling during candidate probes. Update mode and corresponding success information only after candidate generation/session and commit-baseline validation and atomic takeover.
- Expose current-context latest successful remote synchronization time, latest valid synchronization failure time, and safe failure details (category, applicable status code, sanitized description); absent records are null. Success requires valid remote data confirmation/commit, not just a handshake. Success preserves the latest historical failure record; state expresses current health. Accepted valid Identify resets context-owned timestamps and remote confirmation. Late old-generation/session results cannot modify the snapshot. Cache, bootstrap, and TestData local readiness are not remote confirmation; Custom may claim it only when its contract explicitly reports valid remote synchronization.
- Suspension/network loss may retain historical success and confirmation for the current context, but neither implies current connectivity or freshness. Candidate failures use recovery status and safe error information, not active Polling failure records; candidate success enters authoritative records only after takeover. Display timestamps have an explicit UTC representation; timeouts/backoff use monotonic clocks rather than system-clock differences.
- Queries and status subscriptions share one model and update path. Each snapshot is consistent, although state may advance between reads. Event failures remain separate and do not mark flag synchronization failed. Exclude user attributes, SDK keys, authentication headers, credential-bearing URLs, raw response bodies, and unprocessed Throwables from errors. Add no telemetry uploads or server protocol requirements.

### Runtime online/offline contract

- Provide Java/Kotlin-friendly `setOffline()`, `setOnline()`, and explicit offline-state queries; freeze signatures in Phase 1. The offline option sets initial state only. Runtime operations change intent through the coordinator without mutating original options or other frozen configuration. This is an explicit Android extension; common configuration stability does not prohibit these operations.
- Offline queries express application intent, not reachability or service connection success. Calls are idempotent; concurrent transitions follow coordinator acceptance order. Distinguish success, supersession, invalid configuration, closure, and cleanup timeout. Completion means the transition took effect, not remote synchronization completion; online readiness uses a separate bounded current-context wait.
- setOffline atomically prohibits new synchronization requests, fallback/recovery probes, and event delivery; invalidates active transport/candidate sessions and timers; then cancels in-flight requests and stops Custom within a bound. Offline takes precedence over background polling, grace periods, and final Close flush. Late results cannot commit; late errors cannot change mode or recovery scheduling. Cancellation cannot retract already-sent requests, so do not promise the server has not processed them.
- Retain current user, matching memory results, and cache. Offline evaluation reads local values without analytics; Track neither collects nor buffers offline calls. Identify, return-to-anonymous, and anonymous reset still switch local context without networking. Offline clears neither anonymous identity nor automatic attributes; sample only at the agreed creation/Identify points.
- Entering offline settles pending online initialization/Identify waiters as aborted by a mode transition, not successful remote synchronization. New offline calls use local semantics. setOnline neither revives old waiters nor resets budgets. Reconfirm synchronization for the current context; applicable local values remain readable during recovery, but transition alone grants no analytics eligibility to unconfirmed data.
- Seal event groups on entering offline. Previously accepted unconfirmed events stay within existing capacity/retry budgets, with delivery paused and no merging into new post-transition groups. Late invalidated-attempt responses cannot settle new waiters or restart sending. Retrying uncertain batches may duplicate delivery under best-effort semantics. Existing Flush waits finish deferred/offline; offline Flush is a normal empty completion if no work exists, otherwise deferred/offline, never delivered. Offline Close sends nothing, releases the memory queue, and makes unconfirmed-event loss observable.
- Before leaving offline, revalidate frozen configuration for the active path: client key, synchronization endpoints, enabled background polling/fallback, Custom settings, and applicable event endpoints. Offline creation may omit them; insufficient configuration on later setOnline returns a clear error and keeps the instance offline without partial startup. Online operations accept no new credentials/endpoints; completing or changing configuration requires a new instance.
- After online intent takes effect, resume according to visibility, networking, and terminal states. Foreground resumes configured mode and existing fallback policy; background synchronizes only with explicitly enabled polling; Custom follows its pause contract. Events remain gated by foreground state, disableEvents, and event terminal state. Retained events keep original users, timestamps, and groups. Transition alone does not immediately restore Streaming, bypass cooldown, or catch up missed tasks.
- setOnline cannot restart closed instances or clear synchronization terminal states such as 4003 or event terminal states. These states remain independent; healthy subsystems run when permitted. Subscriptions distinguish offline intent, pause/connection state, and terminal reasons. Phase 1 fixes result types, cleanup deadlines, and delivery-attempt generation rules. Cancelling a wait cannot undo an accepted mode transition.

### Private attribute filtering for analytics

- Implement SDK-side filtering only, without server changes. Provide a named private custom-attribute list and all-custom-attributes-private switch, default empty/false, usable from Java/Kotlin. Copy/freeze at creation without a runtime toggle. All-attribute filtering takes precedence. Match exact names without implicit wildcards or nested paths; freeze format and invalid-entry handling in Phase 1.
- Filter only `user.customizedProperties` in evaluation and Track events, including automatic `featbit.sdk.` attributes in that collection. All-filtered means an empty collection. Do not remove user key/name, flag key, variation, metric values, or other fields. Document exclusions without claiming anonymization or concealment of all user information.
- Synchronization/evaluation requests, current immutable context, and cache-matching context keep complete attributes. Filtering must not alter targeting or Identify's effective context; it does not promise sensitive attributes never leave the device. Logs retain independent redaction rules. disableEvents and explicit offline take precedence by prohibiting collection.
- After call-time context capture, create an independent filtered analytics snapshot before queueing; retain neither removed original attributes nor references to the current user object in the queue. Serialization/retries reuse that snapshot. Deduplicate by final sendable payload except timestamp within the flush group: events differing only in private attributes may merge when other fields match. Removed attributes cannot distinguish events. Keep original user key, call time, and established experiment metadata; do not reevaluate flags.
- Verified local server baseline `7ecc24aa`: events accept empty custom attributes; analytics messages omit the collection, but the event endpoint still publishes EndUser updates, and profile updates replace the attribute collection. WebSocket synchronization also publishes complete EndUser data. Filtered events may therefore overwrite profile attributes, and later synchronization may restore them. Promise only that selected attributes are not sent with SDK analytics events, not that the server will not store/reacquire them, erase history, or avoid profile overwrites.

Future server work may separately define event-driven profile updates and synchronization attribute persistence. Do not assume it is solved. Integration runs record actual target versions and observations. Do not automatically modify servers, treat known side effects as filtering failure, or hide newly discovered compatibility issues.

### disableEvents contract

- Provide Java/Kotlin `disableEvents`, default false and frozen at creation; no runtime toggle. Original-option mutation cannot affect running instances. Unlike offline, this disables only analytics; synchronization, Identify, caching, evaluation, subscriptions, and fallback/recovery continue.
- With true, typed, generic, JSON, and detailed evaluation collect no events, and Track collects no metrics. Apply a shared gate before construction/queueing. Retain no user/event payload for later replay; start no sender, periodic flush, or event retry tasks. Values/reasons remain unchanged, and disablement counts as neither failure nor loss.
- Explicit Flush completes within a bound with a normal disabled/no-pending-work result, without networking or claiming delivery; freeze result types in Phase 1. Background and final Close flush also make no requests. Close still cleans up synchronization and resources. Disablement overrides configured intervals, capacity, and background-flush policy.
- Validate event endpoints only when delivery is enabled and requires networking. With disableEvents=true, missing or unused invalid eventsUri cannot prevent creation or affect active synchronization validation. Default false online delivery receives full validation. Independent diagnostics control logs; disableEvents does not disable logging or prevent synchronization requests from sending current user context. Document this boundary.

### Generic evaluation contract

- Provide generic `variation` and `variationDetail` alongside typed and JSON helpers. Freeze public names in Phase 1. Return a unified immutable value model; detailed results include that model, flag key, reason category, and available explanation, not unconstrained `Any`/`Object`.
- Convert the selected server string by declared flag type: specified Boolean conversion, full locale-independent finite Number conversion, unchanged String, or JSON object/array/scalar/explicit null. Unknown/unsupported types or failed conversion return the caller's unified-model fallback and WrongType. Do not guess types or derive successful result types from fallback types.
- Share the value model with parsed JSON helpers, supporting type checks, Java/Kotlin-friendly access/construction, and read-only nested collections. Phase 1 fixes numeric precision/range and wrong-type access. Valid JSON null is a success value distinct from missing flags, parse failure, and host-language null.
- Generic APIs select converters by declared type independently of fallback kind. Typed helpers require matching boolean/number/string declarations; JSON helpers require json. A string flag containing `true` remains a string and fails boolVariation with WrongType. Read-all continues returning raw string details.

Reasons follow FeatBit's common specification without an evaluationReasons switch. Eligible remote reads, including type/parse failures, attempt one event using the selected remote variation, never an extra event for wrapping detailed results. No network/disk I/O.

### Subscription and unsubscription contract

- Global subscriptions report changed key sets; individual subscriptions notify only the selected key. Applications evaluate afterward to read current values. Separate readiness/synchronization subscriptions report failures, suspension, recovery, and terminal states; flag notifications cannot replace them.
- Java registration returns an independent handle with idempotent `close()` for unsubscription, distinct from client closure. Multiple subscriptions per flag are allowed; cancelling one affects neither others nor synchronization.
- Flow and listeners share underlying subscriptions. Change Flows register on collection and release on cancellation/completion; hosts use Android lifecycle to control collection. The SDK cannot infer when ordinary listeners should unsubscribe on page destruction. Document Java page-exit cleanup and Kotlin lifecycle-aware collection.
- Commit complete data and state before notification. Callbacks can read the latest committed value, not necessarily every historical intermediate value. Cover additions, deletions, archival/restoration, effective-value/declared-type changes, and Identify-visible changes. Duplicate or ignored old updates do not notify; do not copy upstream incremental paths that notify unchanged values.
- Individual subscriptions survive deletion/temporary absence, notify unavailability, and continue when the same key returns until unsubscription/SDK closure. Phase 1 fixes initial emission and atomic coordination between initial read and registration to prevent missed updates.
- Java listeners run on Android's main thread by default, outside state locks; Flow execution follows coroutine rules. Isolate each subscriber's recoverable exceptions. Permit evaluation, unsubscription, and close requests in callbacks without one failure affecting others.
- Distinguish observing current values/states from receiving changes. StateFlow may skip intermediate states for slow collectors and must not be described as delivering every change. Change notifications preserve commit order; coalescing retains the union of affected keys and allows current-value reads, rather than retaining only the last notification and losing keys. Phase 1 fixes initial emission, capacity, coalescing, and overflow per API; promise neither unlimited backlog nor lossless historical retention.
- Unsubscription invalidates callbacks not yet started; active callbacks may finish without waiting for themselves. After SDK closure, start no callbacks, release subscriptions/resources, and complete associated Flows. Old-generation pending notifications cannot masquerade as new-context notifications. Coordinate races consistently with state commits.

### Automatic fallback and recovery contract

- Provide Streaming → Polling fallback, disabled by default and separate from explicit Polling. Online enablement requires Streaming and valid endpoints for both transports; reject incompatible/invalid settings before startup. Offline startup still needs no remote endpoints.
- Use FeatBit's existing WebSocket/HTTP Polling protocols without FDv2. Switch after sustained temporary initial-sync or post-connection failures reach a finite threshold. Reset the failure window only on current-context synchronization success, not socket establishment. Phase 1 freezes/publishes thresholds, heartbeat inactivity, and recoverable errors. Retries cannot continually reset the window.
- Fallback thresholds are independent of initialization/Identify wait budgets. Timeout/cancellation neither triggers fallback nor stops recovery. Disabled fallback retains normal Streaming reconnects. Polling cannot bypass 4003/other terminal rejections. Event failures do not trigger synchronization fallback.
- Recovery accompanies fallback for configured Streaming clients; explicit Polling never probes. After cooldown, atomically fence/cancel Polling requests/timers, retain its coherent readable snapshot and open one candidate Streaming session. One deadline includes setup, physical-slot waiting, valid data and takeover. Accept the brief remote-update gap while local reads continue. Release a failed/timed-out candidate and promptly resume eligible Polling; later attempts use capped backoff/jitter, without a fixed lifetime attempt limit.
- Candidates take over only after valid data for the complete current context; handshake/heartbeat success is insufficient. Stage data without affecting public results, persistence, readiness, notifications or analytics. Revalidate deadline, generation/session, permissions and frozen baseline at the atomic commit/authority transfer. Invalid data or baseline mismatch ends the attempt and resumes eligible Polling.
- Capture the baseline's local commit sequence and matching data/cursor when Polling is fenced. Late Polling responses cannot change it; context/lifecycle changes invalidate the attempt. Request full initialization when no usable baseline exists. Use a single candidate and single budget per attempt, without parallel probing, a replacement candidate or split phase budgets. Test that continuing Polling traffic before an attempt cannot starve recovery.
- Identify cancels old candidates and switches Polling context; new probes bind the new generation. Network/foreground resumption does not directly restore Streaming; cooldown and synchronization validation remain required. Preserve backoff after rapid recurring interruption; reset only after Streaming remains synchronized for a specified stability period. Freeze/publish cooldown, probe budgets, backoff caps/jitter, and stability windows in Phase 1.
- Invalidate old Streaming sessions/reconnect tasks before starting Polling. Transports share context/store with one authoritative commit source at a time. Transitions advance session identifiers, rejecting old success/error/close callbacks even without generation changes. Reuse only environment/full-context-matching snapshots/cursors, otherwise request full data. A 304 cannot initialize missing data. Switching neither clears valid results nor implies synchronization success.
- Background, known network loss, offline, terminal, and closed states override fallback/recovery. Switch/probe only when foreground synchronization is permitted; grace periods cannot start new Polling/candidates. Suspension ends the failure window and cancels candidates/deadlines. On foreground/network resumption, non-fallback Streaming observes failures anew; fallback instances resume Polling before cooldown/backoff probes. Retain recovery backoff across lifecycle transitions. Use elapsed time including sleep; handle expired probes and validate state/session on resumed execution, without replaying missed retries or resetting caller budgets.
- Status distinguishes configured/effective modes and fallback/probe/recovery reasons. During recovery retain the Polling fallback selection while explicitly reporting paused Polling and candidate connection; do not claim a live Polling transport. Polling failures use its ordinary backoff. Terminal rejection from effective Polling or an authorized candidate terminates synchronization; stale callbacks do nothing. Preserve event eligibility, Flush and endpoint contracts.

## 9. Development sequence and release gates

Sequence: Phase 1 → 2 → 3 → 4 → 5 → 6 → 7. Tests accompany implementation in each phase; Phase 7 runs combined acceptance rather than deferring all testing until the end.
